# Правила для AI-агентов и разработчиков

Общие правила для всего монорепозитория. Пакетные README (`backend/`, `frontend/`, `mobile/`, `telegram-bot/`) описывают только запуск пакета. Архитектура — в [README.md](README.md), требования — в [docs/Task.md](docs/Task.md).

## Пакеты и инструменты

| Пакет | Стек | Менеджер | Проверки (все должны быть чистыми после любой правки) |
|---|---|---|---|
| `backend/` | FastAPI, async SQLAlchemy, Alembic, PostgreSQL | `uv` | `uv run ruff check . && uv run ruff format --check . && uv run mypy . && uv run pytest` |
| `telegram-bot/` | Python 3.13, long polling | `uv` | то же |
| `frontend/` | Next.js (App Router), Tailwind, Jest + RTL | `pnpm` | `pnpm lint && pnpm typecheck && pnpm test` |
| `mobile/` | React Native (Expo), Jest + RNTL | `pnpm` | `pnpm lint && pnpm typecheck && pnpm test` |

Корневого workspace нет: каждый пакет самостоятельный, со своим lockfile. Команды выполняются из папки пакета.

- Node-проекты: только `pnpm`, никаких `npm`/`yarn`/`npx` (вместо `npx` — `pnpm dlx`).
- Глобальные установки пакетов без согласования не делаем.
- В Expo-проекте библиотеки ставим через `pnpm dlx expo install <package>`, чтобы подобрать версии под SDK.

## Процесс: TDD

Любая фича и любой багфикс: Red → Green → Refactor.

1. Падающий тест, фиксирующий требование или воспроизводящий баг.
2. Запустить, убедиться, что он падает **по ожидаемой причине**.
3. Минимальный код, чтобы тест прошёл.
4. Запустить тесты, убедиться, что всё зелёное.
5. Рефакторинг при зелёных тестах.

Реализацию без падающего теста не пишем. Для багфикса тест воспроизводит баг до правки. Если тест написать нельзя (конфиг, миграции, документация) — говорим об этом явно, а не пропускаем молча. Предпочитаем unit-тесты логики; интеграционные — для API и БД. Тесты не ходят во внешние сервисы (Telegram, LLM, Яндекс.Диск) — только моки.

## Качество кода

- **Python:** type hints на всех параметрах и возвращаемых значениях, без `from x import *`, длина строки ≤ 88, docstring у публичных функций и классов, `async` для I/O.
- **TypeScript:** без `any` (если неизбежно — `// eslint-disable-next-line @typescript-eslint/no-explicit-any` с обоснованием), явные типы возврата у экспортируемых функций, неиспользуемые переменные — ошибка.
- Одна ошибка или предупреждение линтера/типизации — повод остановиться и исправить, а не сдавать работу.
- Минимализм (YAGNI): только то, что нужно текущей задаче; без абстракций и настроек «на потом»; наименьший дифф; комментарии — только про неочевидное «почему».
- Один класс — одна ответственность; логика в сервисах, данные в моделях/схемах.

## Данные и API

- БД одна (PostgreSQL), принадлежит `backend`. Бот, веб и мобильное приложение в БД не ходят — только через API.
- Контракт API — единый OpenAPI (contract-first). Изменение контракта требует ревью владельцев всех затронутых клиентов.
- Миграции Alembic: одна миграция — одно осмысленное изменение с понятным именем; индексы и ограничения именуются по соглашению (`backend/README.md`). Смерженную миграцию не правим.
- Секреты — только в `.env` (в `.gitignore`), в репозиторий попадает лишь `.env.example`.

## Git

- Ветки: `feat/…`, `fix/…`, `docs/…`, `chore/…`. В `main` — только через PR с ревью; force push запрещён.
- Conventional Commits: `feat:`, `fix:`, `docs:`, `refactor:`, `chore:`, `test:`, `ci:`.
- Крупный рефакторинг, который может потребовать отдельной ветки, сначала обсуждаем.

## Особенности пакетов

- **Next.js** меняется между версиями: перед работой с API фреймворка читай актуальную документацию в `frontend/node_modules/next/dist/docs/`, а не полагайся на память.
- **Expo** тоже: смотри мажорную версию `expo` в `mobile/package.json` и документацию `https://docs.expo.dev/versions/v<major>.0.0/` (индекс: `https://docs.expo.dev/llms.txt`). Папки `ios/` и `android/` не создаём и не правим вручную — нативные настройки только через `app.json` и config plugins. После добавления библиотеки с нативным кодом нужен development build.
- `next dev` пересоздаёт `frontend/AGENTS.md` и `frontend/CLAUDE.md`; они в `.gitignore`, не коммитим.
