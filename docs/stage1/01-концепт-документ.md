## 2. Продукт: контекст, а не легенда

Zeta реализуется по варианту «настоящая реализация» (Задание §2.2): это не выдуманная легенда под условного заказчика, а реальный внутренний проект для студентов ФКН. Формально это значит:

- **Заказчик/куратор приёмки** — преподаватель практики.
- **Реальные пользователи** — старосты, заместители старост и студенты ФКН (см. `../Task.md` §1–§2).
- **Бэкграунд и потребность**: расписание ФКН публикуется как Excel на Яндекс.Диске, ДЗ старосты рассылают текстом в чатах подгрупп, информация теряется и не привязана к конкретным парам. Zeta закрывает это без изменения существующего процесса публикации расписания.
- **Рынок/окружение**: закрытая система только для студентов факультета, не электронный журнал, не рассчитана на внешних пользователей.
- **Объективные факторы сроков**: ограничение объёма — прототип должен собираться силами команды из 5 человек за 4 двухнедельных спринта (Задание §2);

Продукт удовлетворяет критериям Задания §2: есть UI и сквозной сценарий (создание ДЗ старостой → просмотр студентом), минимум две роли с разными сценариями (староста / студент), ценность — в предметной логике (привязка ДЗ к конкретной паре расписания, разграничение по подгруппам), а не в технологической новизне.

## 3. Уровень реализации продукта

Выбран вариант **«рабочий прототип, воспроизводящий основной сценарий»** (Задание §2.2): базовый сценарий (авторизация → просмотр расписания и ДЗ → создание ДЗ старостой) реализуется по-настоящему, а не кликабельным макетом. Обоснование — команда уже имеет проработанное техническое ТЗ (`../Task.md`) и намерение довести систему до реального использования на факультете.
